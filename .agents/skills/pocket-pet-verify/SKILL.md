# Проверка Pocket Pet

Выбери проверки по цели пользователя и затронутому поведению. Владелец может проверять продукт после нескольких задач; скилл не требует отдельного подтверждения после каждой правки.

## Контекст

- Найди Git root. Пути ниже относятся к нему; [карта контекста](../../../docs/ai/README.md#карта-контекста) направляет к нужной спецификации и коду.
- Для набора изменений используй указанный пользователем диапазон. Без диапазона начни с локального diff; если он пуст, укажи, что проверяешь текущую версию выбранного сценария, а не всю историю.
- Ожидания бери из GDD и действующей focused spec. Не используй старый отчёт о проверке как доказательство для текущего кода.

## Выбор проверки

- Сборки и статический анализ: команды и область formatter описаны в [agent-tooling.md](../../../docs/specs/agent-tooling.md). Для уже закоммиченных файлов formatter требует `--base <commit>`; пустой локальный diff не означает, что все файлы отформатированы.
- Для интерфейса выбери затронутый сценарий, язык и размер экрана. RU/EN, обе темы, клавиатура, возврат фокуса и мобильная ширина нужны там, где изменение может их затронуть. Используй доступный инструмент браузера и его инструкции; если его нет, опиши границу проверки.
- Для игры проверь авторитетный ответ API и видимое состояние. Для мини-игр особенно важны платное первое начало и бесплатные повторы; для вопросов — сохранение попытки и однократное применение исхода. Точные ожидания бери из spec, не дублируй числа в скилле.
- При изменении обработки ошибок воспроизведи относящийся к задаче отказ, если позволяет окружение. Явно отличай чтение кода от выполненного сценария.

## Окружение и данные

Сначала прочитай [backend guide](../../../docs/backend-guide.md) и проверь существующие процессы/адреса; не запускай второй dev stack поверх первого. Учитывай, что `dev:setup` применяет миграции, а чтение игрового API может пересчитывать и сохранять состояние.

Игровые действия выполняй на отдельных временных гостях/питомцах. Сохрани их точные идентификаторы; при необходимой очистке удаляй только данные, созданные этой проверкой. Не используй питомца владельца как fixture и не применяй reset базы. Если изоляция недоступна, выполни независимые проверки и укажи ограничение.

Не добавляй `*.spec.ts`, постоянный runner, seed-команды или debug API без отдельной задачи. Воспроизводимые состояния и управление временем отложены до [этапа стабилизации](../../../GAME_DESIGN.md#145-после-стабилизации-продукта-воспроизводимые-состояния-для-проверки). Скилл использует доступные возможности, а не реализует этот этап.

## Результат

Кратко сообщи проверенную версию/область, выполненные сценарии и результат, обнаруженные дефекты с воспроизведением и непроверенные случаи. Добавляй скриншоты, когда они помогают оценить интерфейс. Успешная сборка не подтверждает прохождение игрового сценария. Задача проверки сама по себе не разрешает исправлять обнаруженные дефекты или публиковать проект.
