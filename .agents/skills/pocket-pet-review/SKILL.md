# Ревью Pocket Pet

Проверь выбранный diff и ближайший необходимый контекст. Скилл не вводит обязательного ревью каждой задачи и не запускает других агентов.

## Область

Определи Git root и диапазон пользователя. По умолчанию проверяй staged/unstaged изменения и новые файлы. Если diff пуст и диапазон не задан, уточни объект ревью; не выбирай произвольную старую задачу.

Используй [карту контекста](../../../docs/ai/README.md#карта-контекста), соответствующий AGENTS и focused spec. GDD задаёт решения, код — действующее поведение; предположение и открытый вопрос не равны утверждённому требованию. Исторические отчёты могут объяснять причины, но не доказывают отсутствие регрессии.

## Что проверять по затронутой области

- **Время и состояние:** сервер остаётся источником истины; частота polling не меняет результат; финальные состояния и сохранённые итоги согласуются с lifecycle. Числа сверяй со spec.
- **API и данные:** гостевая принадлежность, runtime validation, транзакции и один активный питомец; совместимость миграции с прежними данными. Контроллер, общий пакет `@simple-games/pet-contract`, snapshot и frontend-клиент должны согласоваться.
- **Вопросы и мини-игры:** одна попытка/первое начало не дают повторный эффект; закрытие окна, смена питомца и поздний ответ не возвращают устаревшее состояние. Сопоставляй конкретное поведение со spec активности.
- **Frontend:** серверная доступность действий, порядок запросов, видимые ошибки, отмена таймеров/подписок; новые тексты в RU/EN. Локальная логика партии допустима, расчёт состояния питомца остаётся на сервере.
- **Границы и контекст:** общий контракт не тянет framework/persistence; решение отражено в исходной spec, новый документ — в индексе. Не требуй новый документ или архитектуру ради небольшой правки.

## Проверка и вывод

При необходимости используй существующие lint/build-команды из [agent-tooling.md](../../../docs/specs/agent-tooling.md). Не добавляй тесты: они отложены владельцем. Отсутствие покрытия само по себе не является дефектом этого diff. Не применяй миграции и не меняй пользовательские данные ради статического ревью.

Для каждой находки укажи файл/строку, конкретный триггер, последствие и важность. Отделяй доказанный дефект от предположения; при недостатке доказательств опиши, что осталось проверить. Не наполняй ревью замечаниями о личном стиле, которые уже решает formatter.

Если значимых дефектов нет, сообщи это вместе с границами проверки. Ревью не означает разрешение на исправления, коммит, публикацию или переписывание продуктового решения; выполняй их только в пределах исходного запроса.
