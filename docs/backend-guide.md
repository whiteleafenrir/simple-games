# Backend и база: инструкция для frontend-разработчика

## Ежедневный запуск

Откройте терминал в `D:\_work\simple-games`:

```powershell
npm run dev
```

Оставьте этот терминал открытым. Команда проверит PostgreSQL, синхронизирует схему, сгенерирует Prisma Client и запустит три приложения. При готовности появятся сообщения API, Angular и Studio. Во втором терминале:

```powershell
npm run dev:open
```

| Что открыть | Адрес | Для чего |
| --- | --- | --- |
| Игра | [Pocket Pet](http://localhost:4200/games/pocket-pet) | Пользовательский интерфейс |
| Backend | [Swagger](http://localhost:3000/api/docs) | Список методов API, примеры, выполнение запросов |
| База | [Prisma Studio](http://localhost:5555) | Таблицы, строки, фильтры и редактирование |
| Проверка API и БД | [Health](http://localhost:3000/api/health) | Исправный ответ: `{"status":"ok","database":"up"}` |

`npm run dev:open` только открывает вкладки, запуск делает `npm run dev`. Для отдельной вкладки: `npm run dev:open -- studio` или `npm run api:open`.

Чтобы остановить игру, API и Studio, нажмите **Ctrl+C** в терминале запуска. PostgreSQL продолжит работать, данные останутся. При изменении TypeScript в `apps/api/src` API пересоберётся и перезапустится сам; Angular обновляется своим dev-server. Если в API ошибка компиляции, исправьте её и сохраните файл — nodemon повторит запуск. После правок Prisma schema перезапустите `npm run dev` или примените схему отдельно, как описано ниже.

Если PowerShell блокирует `npm.ps1`, пишите `npm.cmd run dev` и аналогично для остальных команд. Менять execution policy не требуется.

## Что настроено на вашем компьютере

На 7 сентября 2026 года найден и проверен PostgreSQL **17.10**:

- Windows-служба: `postgresql-x64-17`;
- адрес: `127.0.0.1:5435`;
- база: `simple_games`;
- параметры подключения находятся в локальном `.env`; этот файл не попадает в Git.

Старый `.env` указывал порт `5432`. Он исправлен на `5435`, существующая база сохранена. Docker для текущего подключения не нужен.

Проверить только базу:

```powershell
npm run db:status
```

Если служба не работает, откройте **Win+R → `services.msc`**, найдите `postgresql-x64-17` и нажмите «Запустить». В свойствах можно выбрать автоматический запуск, если он ещё не включён. Управление системной службой Windows может потребовать права администратора. Останавливать её после каждого запуска игры не нужно. Команды `db:stop`, `db:logs` и `db:reset` предназначены для Docker; при вашем текущем подключении они откажутся менять базу.

## Смотреть таблицы без написания SQL

Если весь проект уже запущен, просто откройте [Studio](http://localhost:5555). Если нужна только база:

```powershell
npm run db:studio
```

Команда проверяет подключение и открывает Studio. Не запускайте вторую Studio, если первая уже занимает порт `5555`.

Выберите схему `public`, затем таблицу. В Prisma 7 названия отображаются как таблицы PostgreSQL. Отфильтруйте строки по `id`, `guestSessionId` или `petId`.

| Таблица | Что смотреть |
| --- | --- |
| `GuestSession` | Гости. `id` связывает гостя с его питомцами |
| `Pet` | Имя, вид (`petId`), статус, свет, время создания и ухода |
| `PetStats` | Сытость, чистота, счастье, здоровье, энергия питомца |
| `PlayerEnergy` | Энергия игрока для активностей |
| `PetActionCooldown` | Последнее время каждого действия |
| `PetCareAction` | История ухода, статы до и после |
| `PetFarewellResult` | Итог завершённой сессии |

В `Pet` поле **`id` — уникальный номер питомца**, а **`petId` — вид**, например `cat`. В остальных таблицах `petId` ссылается именно на `Pet.id`.

Практика: создайте питомца в игре → найдите его в `Pet` → скопируйте `id` → отфильтруйте `PetStats` и `PetCareAction` по `petId` → выполните кормление в игре → обновите строки Studio. Данные при обычном перезапуске остаются.

В установленной Prisma Studio 7.8 сервер слушает все сетевые интерфейсы (`0.0.0.0:5555`), поэтому не публикуйте этот порт и закрывайте Studio после работы; отдельной авторизации у неё нет.

Studio умеет менять и удалять строки. Такие правки сразу попадают в БД и обходят игровые правила. Для обычной проверки действий используйте игру или Swagger. Удаление `GuestSession` удалит связанных питомцев и историю через каскадные связи. Для экспериментов удобнее отдельное приватное окно браузера: у него своя гостевая cookie.

Статы пересчитываются при API-запросах, фонового тика базы нет. Если игра закрыта, обновление таблицы в Studio само по себе не применяет прошедшее игровое время. Откройте игру или выполните GET питомца через Swagger, затем обновите Studio.

## Смотреть и вызывать backend через Swagger

Откройте [API](http://localhost:3000/api/docs). Раскройте метод, нажмите **Try it out**, заполните поля и нажмите **Execute**.

1. `POST /api/guest-sessions`: отправьте `{}`. Ответ содержит `id` гостя. Браузер сохраняет HttpOnly-cookie автоматически.
2. `GET /api/guest-sessions/{guestId}/pets`: вставьте этот `id`. Увидите своих питомцев.
3. `POST /api/guest-sessions/{guestId}/pets`: создаёт питомца. Пример тела:

```json
{
  "name": "Искорка",
  "petId": "cat",
  "sessionLengthId": "short"
}
```

`short` — 1 день, `standard` — 3 дня, `long` — 7 дней. Если активный питомец уже есть, будет HTTP `409`.

4. Возьмите **`id` питомца из ответа** и передайте в `{petId}` для `POST .../{petId}/actions`:

```json
{"actionId":"feed"}
```

Другие действия: `junkFood`, `clean`, `play`, `walk`, `toggleLight`. В ответе `applied: true` означает успех. `applied: false` с `reason: "cooldown"`, `"sleeping"`, `"away"` или `"player-energy"` — игровое ограничение.

HTTP `400` — некорректные body/поля/UUID (лишние поля также запрещены); `401` — нет действующей cookie, начните с `POST /guest-sessions`; `403` — id гостя не соответствует cookie этого браузера; `404` — сессия или питомец не найдены; `409` — конфликт; `500` — ошибка backend, смотрите терминал `[api]`. GET питомцев также записывает пересчитанное состояние. POST из Swagger выполняет настоящее действие, это не демонстрация.

Публичный guest id не является ключом доступа. API использует секретную cookie `simple_games_guest_token`; её SHA-256 хеш и срок хранятся в БД. В body `POST /guest-sessions` нельзя передавать `guestId`. В production cookie получает `Secure`, поэтому браузерный доступ требует HTTPS.

Игра и Swagger используют одну cookie при открытии на **localhost** в одном профиле браузера: cookie не разделяется по портам. Не смешивайте `localhost` и `127.0.0.1` во вкладках — это разные cookie. OpenAPI JSON: [описание API](http://localhost:3000/api/docs-json). Swagger выключен при `NODE_ENV=production`.

## Полезные команды

| Команда | Результат |
| --- | --- |
| `npm run dev` | База + подготовка Prisma + API + игра + Studio |
| `npm run dev:doctor` | Проверка базы и всех трёх приложений; код 1, если что-то недоступно |
| `npm run dev:backend` | Подготовка БД и только API с автоматическим перезапуском |
| `npm run dev:api` | Только API с перезапуском, когда база и Client уже подготовлены |
| `npm run start:local` | Только Angular; API и БД запускаются отдельно |
| `npm start` | Только Angular с доступом из локальной сети |
| `npm run db:studio` | Только просмотр БД; браузер откроется автоматически |
| `npm run db:status` | Проверка PostgreSQL без запуска API |
| `npm run db:push` | Применить Prisma schema и пересоздать Prisma Client |
| `npm run check` | Генерация Prisma Client и сборки API + Angular, без запуска тестов |

В терминале общего запуска `[api]` — backend и ошибки TypeScript, `[web]` — Angular, `[db-ui]` — Studio. Это основные логи для локальной работы.

## Изменение модели данных

**Обновление существующей БД до T1 (2026-09-08):** остановите приложения и один раз выполните:

```powershell
npx prisma db execute --file prisma/patches/2026-09-08-guest-session-auth.sql
npm run db:push
```

Патч добавляет только nullable-поля авторизации и уникальный индекс, не удаляет строки и допускает повторный запуск. Он нужен потому, что Prisma `db push` предупреждает о новом unique index даже для нового пустого поля; `--accept-data-loss` не требуется. На новой БД достаточно обычного `npm run dev`.

Прежняя cookie `simple_games_guest_id` больше не подтверждает владельца. При первом входе после обновления браузер получит новую сессию; прежние питомцы останутся в БД, но не привяжутся к ней автоматически. По публичному id восстановить доступ через API нельзя. Обычные последующие перезапуски сохраняют новую сессию.

1. Остановите общий запуск по Ctrl+C.
2. Измените `prisma/schema.prisma`.
3. Выполните `npm run db:push`.
4. Если Prisma сообщает о возможной потере данных, остановитесь и проверьте изменение схемы. Обычные команды не соглашаются на удаление автоматически.
5. Запустите `npm run dev` и посмотрите таблицы.

`db push` удобен для текущего локального MVP. Он не создаёт историю SQL-миграций. Перед размещением сервера понадобится baseline migration и процесс `prisma migrate deploy`; это отмечено в аудите. Prisma 7 не запускает генерацию Client после `db push` автоматически, поэтому она включена в npm-команду явно. [Документация Prisma](https://docs.prisma.io/docs/cli/v7/db/push).

## Если что-то не открывается

Начните с `npm run dev:doctor`.

| Симптом | Действие |
| --- | --- |
| База недоступна / `ECONNREFUSED` | Проверьте Windows-службу и порт в `.env`; на вашем компьютере нужен `5435` |
| Ошибка `28P01` | Проверьте пользователя и пароль `DATABASE_URL` |
| Docker не найден | Для текущей машины он не нужен: проверьте, что `.env` не заменён Docker-примером с портом `5432` |
| «Порт ... занят» | Проверьте ранее открытые терминалы и нажмите Ctrl+C в предыдущем dev; не запускайте два экземпляра |
| API остановился после правки | Исправьте ошибку TypeScript в `[api]`, сохраните файл |
| Studio открылась, таблиц нет | Проверьте адрес базы; после первого `npm install` запустите `npm run dev` для создания схемы |
| После сброса базы игра пишет ошибку | Обновите страницу: будет заново восстановлена гостевая сессия |
| После очистки cookie питомцы пропали из игры | Они могут оставаться в БД, но браузер стал новым гостем. Аккаунтов и автоматического восстановления пока нет |

Если меняете `API_PORT` в `.env`, перезапустите общий `dev`: Swagger, health, диагностические ссылки и Angular proxy используют этот порт. Angular остаётся на `4200`, Studio — на `5555`. При первом запуске после обновления `env:ensure` автоматически заменит прежнее имя `PORT` на `API_PORT`. API по умолчанию слушает `127.0.0.1`; Angular proxy позволяет открывать игру из сети через `npm start`, не выставляя API напрямую.

## Первый запуск на другом компьютере

Понадобятся Node.js с npm и PostgreSQL. Проект использует Angular 22 и закреплённый Node **26.1.0** (`.nvmrc`); диапазон `^26.0.0` указан в `package.json`. Эта ветка Node официально поддерживается Angular 22. [Совместимость Angular](https://angular.dev/reference/versions).

Вариант с Docker Desktop:

```powershell
npm install
npm run dev
```

Если `.env` отсутствует, он создастся из `.env.example`. Стандартный Compose PostgreSQL использует `127.0.0.1:5432/simple_games`. Docker Desktop должен быть запущен. Для существующего PostgreSQL сначала выполните `npm run env:ensure`, затем укажите его `DATABASE_URL` и `DB_MODE=external` в `.env`.

`DB_MODE=auto` по умолчанию сначала проверяет уже работающую базу. Автоматически поднимать Docker разрешено только для стандартного подключения Compose; для другого адреса скрипт попросит запустить вашу службу. `DB_MODE=docker` требует совпадения URL с Compose. Это не механизм переключения или переноса данных между базами.

Для Docker доступны `npm run db:stop` (данные остаются) и `npm run db:logs` (последние 100 строк). Полный сброс Docker-данных — отдельная редкая операция: `npm run db:reset -- --confirm-delete-local-data`. Она удаляет volume и всех локальных питомцев; следующий `npm run dev` создаст пустую схему. Для вашей базы на `5435` эта команда заблокирована.

Теория PostgreSQL и Prisma: [небольшой курс](database-course.md). Приоритеты дальнейшей разработки: [аудит проекта](reports/project-audit-2026-09-07.md).
