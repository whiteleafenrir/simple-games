# Аудит Simple Games: архитектура, код, агенты

Дата: **7 сентября 2026**. Обновлено: **8 сентября 2026** после перехода на Angular 22. Базовый commit: `99ecf84`. Аудит выполнен по исходникам и локальному запуску; изменения этой задачи перечислены отдельно. Перед началом worktree был чистым.

## Вывод

Для MVP выбран разумный стек и подходящее разделение: Angular показывает состояние, NestJS обслуживает сценарии, чистые функции engine рассчитывают игру, Prisma сохраняет данные в PostgreSQL. Переписывать проект на другой framework, разбивать на микросервисы или вводить сложную state-management библиотеку сейчас не требуется.

Основной долг находится в корректности сохранения и времени, границе гостевой сессии и согласованности документации. До публичного запуска следует закрыть доступ по чужому guest id и гонки записи. До оценки баланса — исправить зависимость статов от частоты запросов.

Локальная работа с API и БД упрощена в этой задаче. Подробная инструкция: [backend-guide.md](../backend-guide.md).

## Карта архитектуры

```text
Angular components
  → PetStorageService (signal-cache, загрузка/опрос)
  → PetApiService (HTTP /api через dev proxy)
  → Nest controllers
  → PocketPetService (сценарии)
  → pet-engine (время, действия, итог)
  → PocketPetRepository
  → PrismaPocketPetRepository → PostgreSQL

Swagger → те же HTTP endpoints
Prisma Studio → PostgreSQL напрямую, минуя engine
```

**Что стоит сохранить:**

- `pet-engine.ts` отделён от HTTP и БД; можно воспроизводить правила с явно заданным `now`.
- Интерфейс repository отделяет persistence от service. In-memory repository полезен для изолированной проверки, хотя не моделирует гонки SQL.
- Состояние Pocket Pet не живёт в localStorage. LocalStorage используется отдельно для темы и языка, что не нарушает backend source of truth.
- Typed frontend-модели, строгая компиляция TypeScript и Angular templates, централизованные RU/EN тексты.
- В схеме есть внешние ключи, каскадные связи и индексы по гостю/статусу и истории действий.
- GDD фиксирует non-goals и этапы: не нужно преждевременно добавлять аккаунты, механики дракона, предметы или WebSocket.

## Приоритеты

**P1** — исправить до публичного доступа или проверки игрового баланса. **P2** — ближайшие небольшие задачи. **P3** — по мере роста проекта. Статус «Открыто» означает рекомендацию; это не исправлено текущей задачей.

### 1. P1 — Гостевая cookie не защищает доступ к питомцам

**Статус: открыто.** [PetsController](../../apps/api/src/pets/pets.controller.ts), [GuestSessionsController](../../apps/api/src/pets/guest-sessions.controller.ts), `PocketPetService.getGuestSession` и `getOrCreateGuestSession` в [Prisma repository](../../apps/api/src/pets/prisma-pocket-pet.repository.ts).

Контроллеры берут `guestId` из URL и не сравнивают его с cookie. Зная id, можно читать питомцев и выполнять действия без cookie. `POST /guest-sessions` дополнительно принимает произвольный id через тело и может выдать cookie для существующей сессии. HttpOnly защищает cookie от чтения JavaScript, но не заменяет авторизацию запросов. UUID сложно угадать; проблема проявляется при утечке/передаче id, а не означает, что все сессии можно перечислить обычным endpoint.

**Подтверждение:** GET питомцев отдельного временного гостя без Cookie вернул HTTP `200`.

**Что изменить:** определять гостя серверным guard из непрозрачного случайного session token, убрать выбор чужой сессии через body/URL или строго проверять совпадение с авторизованным гостем. Перед публичным HTTPS добавить production cookie policy (`Secure`, lifetime) и ограничения частоты выдачи гостей/действий. Same-origin proxy оставить.

**Критерий:** второй гостевой контекст не может читать или менять первого, даже зная его публичный guest id. В этой задаче API ограничен loopback по умолчанию и убран permissive CORS, но дефект авторизации этим не исправлен.

### 2. P1 — Чтение и запись состояния не образуют одну защищённую операцию

**Статус: открыто.** `PocketPetService.applyCareAction`, `resolveAndSave`, `PrismaPocketPetRepository.savePet`.

Service читает snapshot, рассчитывает результат, затем вызывает transaction только для записи. Другой запрос успевает прочитать то же старое состояние. Два действия могут пройти один cooldown/бюджет энергии, а более поздний save затрёт результат первого. Даже GET, обновляющий состояние по времени, может записать snapshot поверх только что выполненного действия.

**Что изменить:** перенести read → resolve → apply → save в одну операцию repository с блокировкой строки либо ввести optimistic concurrency (`version` и условный update с повтором). Проверку cooldown и энергии выполнять на защищённом актуальном snapshot. Для повторов HTTP рассмотреть idempotency key.

**Критерий:** два одновременных запроса не теряют изменения и не расходятся между историей и текущими статами. Это вывод из границ transaction; полноценный нагрузочный прогон не выполнялся.

### 3. P1 — Правило одного активного питомца защищено только service-проверкой

**Статус: открыто.** `PocketPetService.createPet`, [schema.prisma](../../prisma/schema.prisma), модель `Pet`.

Два запроса создания могут одновременно пройти `existingPets.some(...)` и оба записать питомца. Индекс `[guestSessionId, status]` не является уникальным.

**Что изменить:** сериализовать создание на уровне гостя и добавить DB-инвариант: например, partial unique index по `guestSessionId` для `status='pet'` в SQL migration. Конфликт обрабатывать как HTTP `409`. При внедрении сначала проверить, нет ли уже дубликатов активных питомцев.

**Критерий:** при конкурентном создании ровно один запрос успешен, остальные получают понятный конфликт.

### 4. P1 — Частые запросы останавливают ухудшение статов

**Статус: открыто, воспроизведено.** [pet-engine.ts](../../apps/api/src/pets/pet-engine.ts): `resolvePetState`, `normalizeStats`, `roundStat`, `healthDecay`.

Каждый resolve округляет статы до 0.1 и переносит `lastResolvedAt`. Потерянная дробная часть не накапливается. При стандартном frontend-опросе каждые 30 секунд изменения большинства статов меньше 0.05 и исчезают.

Проверка одного и того же нового кота, без действий, за 1 час:

| Стат | Один resolve через час | Resolve каждые 30 секунд |
| --- | ---: | ---: |
| satiety | 77 | 80 |
| cleanliness | 78 | 80 |
| happiness | 78.5 | 80 |
| health | 84.6 | 85 |
| energy | 73.8 | 75 |

Кроме округления, `healthDecay` оценивает stress по статам **в начале** всего интервала. Большой offline-интервал и серия коротких интервалов могут дать разное здоровье при пересечении порогов 45/25.

**Что изменить:** хранить достаточную точность, округлять только отображение; рассчитывать изменение здоровья с учётом пересечения порогов или через фиксированные серверные шаги времени. Продуктовая цель — одинаковый результат для одного elapsed time и одинаковой истории действий независимо от polling.

**Критерий:** расчёт за час/сутки одним шагом и частями даёт эквивалентный результат с оговорённой погрешностью. Баланс-коэффициенты отдельно не менять, пока не устранён этот дефект.

### 5. P1 — ID истории не уникален между питомцами

**Статус: открыто, воспроизведено.** `createCareActionEntry` в engine, `PetCareAction.id @id` в Prisma, цикл `savePet.careHistory`.

ID строится как `actionId-timestamp-historyLength`. Два разных питомца с одинаковой длиной истории и действием в одну миллисекунду получают одинаковый ID. Repository ищет существующую запись только по этому ID и может пропустить сохранение истории второго питомца.

**Подтверждение:** первые `feed` двух объектов с разными `pet.id` и общим `now` получили одинаковое значение `feed-1788220800000-1`.

**Что изменить:** включить `pet.id` в детерминированный ID либо создавать UUID события на границе service; совместить с защитой параллельных действий. Не считать существующую запись чужого питомца успешно сохранённым событием.

**Критерий:** действия разных питомцев в один момент сохраняются независимо, повтор одного события не создаёт дубль.

### 6. P2 — Отсутствующее тело запроса вызывает HTTP 500

**Статус: открыто, воспроизведено.** `PocketPetService.createPet` и `applyCareAction`, HTTP-контроллеры.

Отдельные значения проверяются `parse*` функциями, но само `request` не проверяется. TypeScript interface исчезает во время выполнения. POST actions без тела привёл к `Cannot read properties of undefined (reading 'actionId')` и HTTP `500`.

**Что изменить:** проверять форму body на входе, выбрать typed DTO + ValidationPipe или небольшие явные parser-функции; определить поведение для лишних полей и UUID. Возвращать `400`, не исключение сервера. Swagger, добавленный сейчас, описывает формат, но сам не валидирует входящие данные.

**Критерий:** отсутствующее/некорректное тело и неверные значения дают предсказуемые ошибки `400`; корректный запрос сохраняет прежнее поведение.

### 7. P2 — Динозавр механически отличается вопреки MVP-решению

**Статус: открыто.** `PocketPetService.petModeForPetId`, `pet-engine.modeDecayMultiplier`, [pocket-pet.config.ts](../../src/app/pocket-pet/pocket-pet.config.ts), GDD §6.

Species traits нейтральные, но динозавр получает `medium`, а это множитель ухудшения 1.2. Кошка/собака/попугай получают `easy`. GDD одновременно описывает это как текущее состояние и требует одинаковых механик видов в MVP.

**Что изменить:** привести игровое исполнение к принятому MVP-решению — убрать влияние species-derived mode на базовые виды, согласовать UI и обработку уже сохранённых питомцев. Не просто менять traits: различие находится в другом множителе.

**Критерий:** одинаковые начальные состояния разных разрешённых видов за одинаковое время меняются одинаково. Изменение требует отдельной маленькой продуктовой спецификации/пометки, потому что затрагивает баланс и сохранённые данные.

### 8. P2 — Prisma repository обходит типизацию и маскирует повреждённые значения

**Статус: открыто.** [prisma-pocket-pet.repository.ts](../../apps/api/src/pets/prisma-pocket-pet.repository.ts): `prismaClient`, `toOwnedPet`, `normalize*`.

Client и transaction приводятся к `Record<string, any>`, поэтому компилятор не проверяет реальные имена полей, include и данные update/create. Неизвестный action превращается в `feed`, неизвестный вид — в `cat`, некорректная дата — в Unix epoch. Ошибка данных выглядит как нормальный питомец.

**Что изменить:** использовать `Prisma.TransactionClient`, generated payload types и `satisfies` для include; оставить явное преобразование Date → ISO. Для legacy-данных нужны отдельные известные правила миграции; неожиданные значения следует диагностировать, а не молча переименовывать.

**Почему:** изменение Prisma schema начнёт выявлять несовместимый repository при сборке, а не после записи неверной истории.

### 9. P2 — Polling перезаписывает всю историю и создаёт много SQL-запросов

**Статус: открыто.** `listPets`, `petInclude`, `savePet` в service/repository.

Каждая загрузка списка включает всю историю всех питомцев. Service последовательно resolve/save каждого, включая завершённых. Save обновляет статы, энергию, шесть cooldown и farewell, затем делает `findUnique` для каждого исторического события. Даже чтение становится большим числом записей и N+1 запросов; стоимость растёт с историей гостя.

**Что изменить:** отделить список/текущий snapshot от истории; загружать историю отдельным paginated запросом; добавлять только новые события; не сохранять неизменившихся завершённых питомцев. По возможности использовать typed upsert/nested writes и избегать повторного чтения всего aggregate.

**Критерий:** число SQL-запросов для обычного опроса активного питомца не растёт пропорционально всей накопленной истории. Это оценка по коду, количественный SQL benchmark не выполнялся.

### 10. P2 — Два таймера и устаревшие ответы могут откатывать UI

**Статус: открыто.** [PetStorageService](../../src/app/pets/pet-storage.service.ts), [PocketPetComponent](../../src/app/pocket-pet/pocket-pet.component.ts).

Service опрашивает раз в 60 секунд, компонент — раз в 30. Есть дополнительные загрузки при инициализации. Запросы могут накладываться друг на друга, на создание и действие. Более старый ответ списка может прийти после нового ответа action и заменить cache устаревшими статами. In-flight флага создания/действия нет, поэтому повторные клики легко создают параллельные команды.

**Что изменить:** один источник polling в store; сериализация или отмена устаревшей загрузки; версия/номер запроса для применения ответа; pending-состояния для команд. Останавливать polling в скрытой вкладке и обновлять при возвращении. Это дополнение к серверной защите, не её замена.

**Почему:** меньше трафика и ложных откатов интерфейса, более понятный отклик на нажатие.

### 11. P2 — Ошибка синхронизации может быть скрыта следующей загрузкой

**Статус: открыто.** `PetStorageService.initialize`, `loadPets`, `addPet`, `careForPet`.

`loadPets` ловит ошибку и не пробрасывает её, а `initialize` после `await loadPets` безусловно очищает `syncError`. Ошибка первоначальной загрузки может стать невидимой. После ошибки create/action выполняется `resolvePets`; успешный GET очищает ошибку команды. UI способен показать «активный питомец уже есть» вместо ошибки валидации или вовсе не объяснить отказ.

**Что изменить:** разделить ошибки загрузки и команды; возвращать явный результат загрузки или пробрасывать её ошибку; отображать коды API через переводимые тексты. Не очищать ошибку действия успешным фоновым GET.

**Критерий:** первый failed GET, потеря сети, `400` и `409` имеют разные понятные состояния, успешная повторная команда очищает собственную ошибку.

### 12. P2 — Нет истории изменений схемы БД

**Статус: открыто.** [prisma.config.ts](../../prisma.config.ts), `prisma/schema.prisma`, npm scripts. Путь migrations указан, но зафиксированных migrations нет.

`db push` подходит для прототипа, однако не объясняет, как обновлять уже заполненную базу на другом окружении, воспроизводить partial indexes и откатывать прикладные изменения.

**Что изменить:** перед первым shared/production окружением оформить baseline текущей базы, затем SQL migrations в Git и отдельный deployment flow. Не запускать `migrate reset` по существующим данным для обхода drift. Бэкап/восстановление проверить до важных данных.

**Почему:** запуск нового checkout и обновление существующей базы становятся предсказуемыми. `db push` оставлен для текущего локального MVP; автоматический destructive reset не добавлялся.

### 13. P2 — DTO frontend/backend описаны дважды

**Статус: открыто.** [pet-domain.types.ts](../../apps/api/src/pets/pet-domain.types.ts), [owned-pet.model.ts](../../src/app/pets/owned-pet.model.ts), `pocket-pet.model/config.ts`.

Повторяются статусы, action ids, shapes snapshot/history/result; длительности сессий есть и в API, и в frontend. Одна сторона может измениться и продолжить успешно собираться с несовместимым контрактом.

**Что изменить:** маленький общий пакет только для transport types либо генерация клиента из полного OpenAPI. Не импортировать backend engine в Angular. Gameplay-константы остаются на сервере; UI получает метаданные или отдельно сверяет значения.

**Почему:** контракт меняется согласованно. Текущий Swagger описывает запросы и методы, но полные response schemas ещё стоит добавить перед генерацией клиента.

### 14. P2 — Runtime обновлён и закреплён; CI ещё не добавлен

**Статус: частично исправлено 2026-09-08.** `package.json`, `.nvmrc`, `apps/api/tsconfig.json`, `.github`.

Проект обновлён с Angular 21 до Angular `22.1.5`, CLI/build `22.1.7` и TypeScript `6.0.3`. Angular 22 официально поддерживает Node `^26.0.0`, поэтому установленный Node `26.1.0` теперь входит в матрицу. Версия закреплена через `.nvmrc`, диапазон `engines.node`, `packageManager`; `@types/node` соответствует ветке 26. [Совместимость Angular](https://angular.dev/reference/versions).

Официальные миграции Angular сохранили прежнюю стратегию change detection через `ChangeDetectionStrategy.Eager`, XHR backend через `withXhr()` и семантику optional chaining в одном шаблоне. Для TypeScript 6 удалены устаревшие `baseUrl`/`downlevelIteration`, а NestJS API переведён с `node`/CommonJS options на согласованные `Node16` module options. Optional CLI migrations не применялись: проект уже использует application builder, а Karma-конфигурации нет.

**Что осталось:** добавить CI с `npm ci`, Prisma generate, API build и Angular build. Сейчас `.github` содержит PR template, но workflow сборки отсутствует. Новое тестовое покрытие в CI не навязывать до отдельной задачи. `npm run check` уже объединяет генерацию Client и две сборки.

### 15. P3 — Декомпозиция frontend нужна точечно

**Статус: предложение.** Компоненты Pocket Pet и двух профилей, `pet-display.utils.ts`, [app.routes.ts](../../src/app/app.routes.ts).

Форматирование дат, статов и label-методы повторяются между экранами; `careHistory()` разворачивает массив заново при вычислении шаблона. Все маршруты загружаются eager. Это не причина крупной переписи: после Angular 22 production initial bundle около 401 kB raw, ниже настроенного warning 500 kB.

**Что изменить:** по мере изменений вынести общие stat/history/farewell представления и чистое форматирование; вычислять reverse-history через computed. При росте включить route-level `loadComponent`, начиная с отдельной мини-игры. Выбор NgRx сейчас не обоснован размером состояния.

**Почему:** меньше рассинхронизации интерфейса и повторного кода без архитектурной церемонии.

### 16. P3 — Настройки и тексты UI требуют небольшого прохода

**Статус: открыто.** [user-settings.service.ts](../../src/app/settings/user-settings.service.ts), `users/user.service.ts`, `i18n/translations.ts`.

`localStorage.getItem` находится вне try/catch, `setItem` тоже не защищён. Запрет storage или ошибка записи могут сломать создание сервиса настроек. Пользователь пока фиктивный (`temp-user`), что допустимо для MVP, но привязку settings key к нему стоит упростить до guest/application preferences до аккаунтов. Тексты для игрока упоминают backend, guest id и запуск API.

**Что изменить:** обернуть чтение/запись в безопасный fallback к memory/defaults; при стабилизации UX заменить технические формулировки на понятное состояние «Не удалось связаться с питомником». Техническую инструкцию оставить developer-инструментам и документации.

**Почему:** локальные предпочтения не блокируют всю игру, а пользовательский интерфейс не требует знания реализации.

### 17. P2 — Инструкции агентов и шаблоны противоречили друг другу

**Статус: исправлено в этой задаче для актуального workflow.** Корневой AGENTS запрещает добавление/расширение `*.spec.ts` без явного запроса, но PR template требовал обновить тесты и выполнить `npm test`. Implementation plan template требовал `Test first`. Специализированные engine-инструкции лежали только под `src/app/pets`, хотя engine перенесён в API.

**Что изменено:** добавлен [apps/api/AGENTS.md](../../apps/api/AGENTS.md), ссылка на него в корневом AGENTS; обновлены команды полного запуска и диагностики; PR/spec/plan templates согласованы с MVP; в backend-инструкциях зафиксированы важные границы persistence и контракта. Инструкции frontend оставлены в своей области.

Расположение AGENTS имеет значение: Codex объединяет инструкции от корня вниз к рабочей директории, более близкие имеют приоритет. Поэтому полагаться только на файл в соседней frontend-папке для API-задач не стоит. Корневой AGENTS теперь явно направляет читать нужный scope. [OpenAI Docs: AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md).

**Рекомендация:** держать по одному короткому источнику правил на область, не копировать целиком GDD во все инструкции. Подключать subagents, дополнительные skills или тяжёлый процесс только при реальной задаче, требующей их. Текущему размеру проекта не нужен отдельный orchestration framework.

### 18. P2 — Документация смешивала планы и действующее состояние

**Статус: исправлено в части структуры; продуктовые вопросы остаются открытыми.** README, GDD, `docs/specs/README.md`, `docs/plans/backend-mvp-implementation.md`, старый `backend-mvp-issues.md`.

README описывал уже реализованный backend как roadmap и утверждал обязательность Docker. Старые инструкции привязывали БД к `5432`, хотя действующая служба использует `5435`. Шаблоны ещё говорили о тестах как обязательном gate. В GDD формулировка «средний care score» неоднозначна: engine усредняет пять **финальных статов**, а не заботу за всё время сессии. Ритм утро/вечер описан как цель, но текущий сон — простой переключатель света без календаря.

**Что сделано:** README сокращён, добавлен единый практический backend guide, обновлены ссылки/старый курс, прежние отчёт и implementation plan помечены историческими, новая dev-spec фиксирует принятые изменения. Технические находки сгруппированы в этапы `T0–T6` в GDD, а продуктовые вопросы собраны в GDD §16.

**Что осталось:** после продуктового решения явно уточнить score (финальный snapshot или история за сессию), смысл дневного ритма и расхождение neutral species/mode. Эти вопросы не блокируют синхронизацию документов и записаны как open questions. Новые решения в рамках аудита не выдумывались.

### 19. P2 — Граница локальных инструментов и публикации

**Статус: частично улучшено.** `apps/api/src/main.ts`, `compose.yaml`, Prisma Studio 7.8 CLI.

API раньше слушал `0.0.0.0` и отражал произвольный CORS origin. Теперь по умолчанию `HOST=127.0.0.1`, dev frontend использует same-origin proxy, Swagger не включается в production. Docker-порт базы уже ограничен loopback. Эти настройки не заменяют гостевую авторизацию из пункта 1.

**Наблюдение:** Prisma Studio 7.8 в этой установке слушает `0.0.0.0:5555`; CLI не предоставляет hostname-флаг в `--help`. Уже существовавшая команда Studio имела такое же поведение. Доступность с других машин зависит от сети и firewall. Поэтому Studio следует считать административным инструментом разработчика, не публиковать через reverse proxy и закрывать после работы. В текущей задаче firewall и системные сетевые настройки не менялись.

**Что изменить перед размещением:** production same-origin routing, доверенные origins при действительно раздельных доменах, cookie security и guest guard, ограничения запросов, проверка backup/restore. Для постоянно работающего редактора БД выбрать инструмент/режим с явным loopback bind или контролируемой авторизацией. Не пытаться решить это переписыванием всей архитектуры MVP.

## Исправления локального workflow в этой задаче

1. Исправлен **локальный `.env`**: существующая база на `5435` вместо неработающего `5432`; учётные данные не выводились в отчёт, `.env` остаётся вне Git.
2. `db:start` использует работающий PostgreSQL из `.env`; Docker запускает только для стандартного Compose-подключения. Есть режим `external` и понятные ошибки вместо обязательного Docker.
3. `dev` запускает Angular, nodemon API и Studio через `concurrently`, выводит адреса и проверяет занятые порты. Исправлена прежняя конструкция `spawn('npm.cmd', ..., {shell:false})`: `.cmd` требует Windows shell; управление фиксированными npm-командами передано `concurrently`. [Документация Node](https://nodejs.org/api/child_process.html#spawning-bat-and-cmd-files-on-windows).
4. `db:push`/`prisma:migrate` явно запускают `prisma generate`, поскольку Prisma 7 больше не делает это автоматически. [Prisma db push](https://docs.prisma.io/docs/cli/v7/db/push).
5. Добавлены `dev:doctor`, `dev:open`, `api:open`, `dev:backend`, `db:status`, `db:logs`, `check`; `db:studio` только подключается к БД и не применяет схему ради просмотра.
6. Добавлены health и Swagger с примерами запросов/описаниями. Использована совместимая с Nest 11 ветка `@nestjs/swagger@11`; major upgrade Nest не делался. [Nest OpenAPI](https://docs.nestjs.com/openapi/introduction).
7. Angular proxy переведён на `proxy.conf.cjs`, чтобы он читал `API_PORT` из `.env`. Отдельное имя переменной не конфликтует с обработкой `PORT` в Angular CLI 22; `env:ensure` автоматически мигрирует старый локальный `.env`.
8. Сброс Docker volume требует явного флага и не применяется к внешней базе. Обычный запуск не использует `--accept-data-loss` или `--force-reset`.
9. Добавлена [dev-spec](../specs/local-development.md), [инструкция](../backend-guide.md), синхронизированы README и agent workflow.

Игровой engine, Prisma schema, существующие питомцы и backend-сценарии заботы не переписывались. Изменения API-контроллеров — документация методов; новая функциональность API — health и dev Swagger.

## Предлагаемый порядок следующих задач

Порядок синхронизирован с [техническим треком GDD](../../GAME_DESIGN.md#144-техническая-готовность-и-очередность). GDD определяет этап и условие готовности; этот аудит хранит причины, воспроизведение и конкретные рекомендации.

1. `T1` — гостевой guard и runtime validation (пункты 1 и 6).
2. `T2` — единая защищённая операция изменения состояния, один активный питомец, уникальные события (2, 3, 5).
3. `T3` — независимость времени от polling и нейтральные MVP-виды (4, 7), затем оценка баланса.
4. `T4` — typed persistence, упрощение SQL/read flow, frontend-cache и ошибки (8–11).
5. `T5` — baseline migrations, общий контракт, закреплённый runtime и CI сборок (12–14); обязателен до первого shared/deploy окружения.
6. `T6` — UI-декомпозиция и финальная редактура текстов по мере стабилизации UX (15, 16).

Пункт 17 и выполненная локальная часть пунктов 18–19 относятся к `T0`. Оставшиеся требования пункта 19 входят в `T5` перед публикацией. При закрытии пункта нужно обновить его статус и доказательство здесь, затем статус соответствующего этапа в GDD.
