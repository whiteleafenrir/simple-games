## Карта архитектуры

```text
Angular components
  → PetStorageService (signal-cache, загрузка/опрос)
  → PetApiService (HTTP /api через dev proxy)
  → Nest controllers
  → PocketPetService (сценарии)
  → pet-engine (время, действия, итог)
  → PocketPetRepository
  → PrismaPocketPetRepository → PostgreSQL

Swagger → те же HTTP endpoints
Prisma Studio → PostgreSQL напрямую, минуя engine
```

**Что стоит сохранить:**

- `pet-engine.ts` отделён от HTTP и БД; можно воспроизводить правила с явно заданным `now`.
- Интерфейс repository отделяет persistence от service. In-memory repository полезен для изолированной проверки, хотя не моделирует гонки SQL.
- Состояние Pocket Pet не живёт в localStorage. LocalStorage используется отдельно для темы и языка, что не нарушает backend source of truth.
- Typed frontend-модели, строгая компиляция TypeScript и Angular templates, централизованные RU/EN тексты.
- В схеме есть внешние ключи, каскадные связи и индексы по гостю/статусу и истории действий.
- GDD фиксирует non-goals и этапы: не нужно преждевременно добавлять аккаунты, механики дракона, предметы или WebSocket.

### 1. P1 — Гостевая cookie не защищает доступ к питомцам

**Статус: исправлено 2026-09-08 (T1).** [PetsController](../../apps/api/src/pets/pets.controller.ts), [GuestSessionsController](../../apps/api/src/pets/guest-sessions.controller.ts), [GuestSessionGuard](../../apps/api/src/pets/guest-session.guard.ts), [авторизация](../../apps/api/src/pets/guest-session-auth.service.ts), [Prisma repository](../../apps/api/src/pets/prisma-pocket-pet.repository.ts).

На момент аудита контроллеры брали `guestId` из URL без авторизации. Зная id, можно было читать питомцев и выполнять действия без cookie; `POST /guest-sessions` принимал произвольный id через тело и выдавал cookie для существующей сессии. HttpOnly защищает cookie от чтения JavaScript, но не заменяет авторизацию запросов. UUID сложно угадать; проблема проявлялась при утечке/передаче id.

**Подтверждение:** GET питомцев отдельного временного гостя без Cookie вернул HTTP `200`.

**Что исправлено:** guard всех защищённых методов определяет гостя по случайному token из 32 байт в HttpOnly-cookie; БД хранит только SHA-256 хеш и срок действия. URL должен принадлежать авторизованному гостю; выбор гостя через body запрещён. Cookie живёт 365 дней, имеет `SameSite=Lax` и `Secure` в production, сервер проверяет истечение. Публичные DTO не раскрывают credential-поля. Старые id-cookie не принимаются, данные остаются в БД. [Спецификация и обновление схемы](../specs/backend-source-of-truth.md).

**Проверка критерия:** ручной HTTP smoke на Nest + PostgreSQL подтвердил `401` без cookie и с подделкой token/id/хеша, `403` с cookie второго гостя на всех пяти защищённых маршрутах, `404` для чужого pet id внутри своей сессии. Отказы не изменили строки первого гостя и его питомца. Проверены восстановление сессии, истечение token, отклонение старой cookie, `Secure` в production и Swagger. Всего вместе с A6 выполнено 68 проверок HTTP-статусов; временные гости удалены, исходные количества гостей/питомцев сохранены. Ограничения частоты запросов остаются отдельной задачей перед публикацией (граница общего окружения, A19).

### 2. P1 — Чтение и запись состояния не образуют одну защищённую операцию

**Статус: исправлено 2026-09-08 (T2).** [Service](../../apps/api/src/pets/pocket-pet.service.ts), [Prisma repository](../../apps/api/src/pets/prisma-pocket-pet.repository.ts), [контракт транзакции](../../apps/api/src/pets/pocket-pet.repository.ts).

На момент аудита service читал snapshot, рассчитывал результат и запускал transaction только для записи. Параллельное действие или GET могли перезаписать новое состояние старым, повторно пройти cooldown или потратить одну энергию.

**Что исправлено:** все сценарии питомцев проходят через одну interactive transaction с блокировкой строки гостя (`FOR UPDATE`, `ReadCommitted`). Чтение, resolve/apply, статы, cooldown, энергия, farewell и история используют один `Prisma.TransactionClient`. Серверное время берётся после блокировки. Транзакционный интерфейс ограничен одним гостем, in-memory repository реализует очередь и commit копии состояния. HTTP idempotency key отдельно не вводится: повторная команда проходит игровые ограничения.

**Проверка критерия:** ручной smoke на двух экземплярах API с отдельными Prisma-подключениями: 12 одинаковых кормлений дали одно действие и 11 cooldown; разные действия вперемешку с восемью GET сохранили все события, статы и энергию. Из двух действий на последние 15 единиц энергии прошло одно. 12 переключений света в одну миллисекунду сохранились в порядке выполнения. Искусственная ошибка после записи полностью откатила гостя, питомца и дочерние строки. Другой гость продолжал работать при удерживаемой блокировке; ожидавший запрос получил время после её освобождения. In-memory очередь, cooldown и rollback также проверены.

**Граница:** это проверка конкурентных сценариев MVP, а не нагрузочный benchmark на длинной истории. Стоимость чтения истории отдельно проверена и исправлена в A9/T4 ниже. В прогоне pg выдал deprecation warning о постановке запроса на занятое соединение; проверки завершились успешно, обновление драйвера не входило в T2.

### 3. P1 — Правило одного активного питомца защищено только service-проверкой

**Статус: исправлено 2026-09-08 (T2).** `PocketPetService.createPet`, [schema.prisma](../../prisma/schema.prisma), [SQL-патч](../../prisma/patches/2026-09-08-pet-write-integrity.sql).

На момент аудита два запроса могли пройти предварительную проверку и создать по активному питомцу. Индекс по гостю/статусу был неуникальным.

**Что исправлено:** создание сериализовано на уровне гостя. Частичный unique index `Pet_one_active_per_guest` запрещает две строки `status='pet'` для одного `guestSessionId`. Он описан в schema через `partialIndexes` Prisma 7.8 и сохраняется при `db push`. Применение SQL-патча проверяет старые дубликаты под блокировкой таблицы и останавливается без изменения данных при конфликте. Нарушение индекса переводится в `409`, включая локализованные сообщения PostgreSQL, где PrismaPg не возвращает `target`.

**Проверка критерия:** на исходной БД дубликатов не было. Из 16 одновременных HTTP-созданий прошёл один запрос, 15 получили `409`; в БД один активный питомец. Восемь конкурентных созданий после истечения прежней сессии сохранили один farewell и одного преемника. Прямая вставка второго активного питомца в PostgreSQL отклонена уникальным индексом; проверено преобразование DB-ошибки в domain conflict. SQL-патч применён без удаления данных, `npm run db:push` подтвердил синхронизацию схемы.

### 4. P1 — Частые запросы останавливают ухудшение статов

**Статус: исправлено 2026-09-17 (T3).** [pet-engine.ts](../../apps/api/src/pets/pet-engine.ts): `resolvePetState`, `normalizeStats`, `resolvePlayerEnergy`, `healthDecay`.

На момент аудита каждый resolve округлял статы до 0.1 и переносил `lastResolvedAt`. Потерянная дробная часть не накапливалась. При стандартном frontend-опросе каждые 30 секунд изменения большинства статов были меньше 0.05 и исчезали.

Проверка одного и того же нового кота, без действий, за 1 час:

| Стат | Один resolve через час | Resolve каждые 30 секунд |
| --- | ---: | ---: |
| satiety | 77 | 80 |
| cleanliness | 78 | 80 |
| happiness | 78.5 | 80 |
| health | 84.6 | 85 |
| energy | 73.8 | 75 |

Кроме округления, `healthDecay` оценивал stress по статам **в начале** всего интервала. Большой offline-интервал и серия коротких интервалов давали разное здоровье при пересечении порогов 45/25.

**Что исправлено:** статы и энергия игрока сохраняют дробную точность при resolve, действиях и чтении через Prisma; округление осталось в отображении и care score. Здоровье рассчитывается по участкам между пересечениями порогов 45/25, включая восстановление энергии во сне. Базовые скорости сохранены. Численная погрешность учитывается при проверке порогов настроения, достаточности энергии и времени её восстановления; `lastResolvedAt` ограничен концом сессии и не отматывается назад. [Спецификация T3](../specs/backend-source-of-truth.md#t3-время-и-нейтральность-видов-решение-2026-09-17).

**Проверка критерия:** ручной smoke с заданным временем сравнил час/сутки/неделю одним шагом, с шагами 1 секунда, 30 секунд и нерегулярными интервалами; 150 дополнительных сценариев с разными начальными статами и сном. Вместе с действиями/видами выполнены 2532 числовых сравнения, максимальная разница `4.79e-10` при допуске `1e-8`. Проверены документированные часовые скорости, здоровье при пересечении обоих порогов в обе стороны, ограничения 0..100, cooldown/сон/прогулка, точный момент доступности энергии, поздний farewell и отсутствие повторного decay. Время восстановления дополнительно проверено на каждой секунде до накопления стоимости действия.

**Persistence:** на PostgreSQL — 120 последовательных GET через service/repository с шагом 30 секунд, сравнение с одним GET за час, сохранение/чтение дробей, дневной интервал, legacy mode, история действий, параллельные GET/заблокированное кормление и неизменность farewell. 22 числовых сравнения, максимальная разница `5.41e-13`. Четыре временных гостя удалены; исходные количества гостей, питомцев и событий сохранены. Схема не менялась. Драйвер pg повторил известный deprecation warning T2; проверка прошла. `npm run check` успешен; после уточнения времени восстановления энергии повторены сборка API и smoke. Новые `*.spec.ts` не добавлялись, существующие не запускались.

### 5. P1 — ID истории не уникален между питомцами

**Статус: исправлено 2026-09-08 (T2).** `createCareActionEntry` в [engine](../../apps/api/src/pets/pet-engine.ts), сохранение истории в Prisma/in-memory repositories.

При аудите ID строился как `actionId-timestamp-historyLength`. Два разных питомца с одинаковой длиной истории и действием в одну миллисекунду получали одинаковый ID; repository мог молча пропустить запись второго питомца.

**Подтверждение:** первые `feed` двух объектов с разными `pet.id` и общим `now` получили одинаковое значение `feed-1788220800000-1`.

**Что исправлено:** новый ID содержит `pet.id`, последовательный номер с ведущими нулями, действие и время. Сортировка по времени/id сохраняет порядок новых событий одной миллисекунды. Повторное сохранение события не создаёт дубль; совпадение id с другим владельцем или содержимым откатывает всю транзакцию. Старые ID не переписываются.

**Проверка критерия:** кормления двух питомцев в одну миллисекунду сохранились независимо с разными id. Повторные save одного snapshot не добавили строку. Чужой event id и изменённое содержимое существующего события вызвали rollback без изменения исходного состояния; порядок 12 событий одной миллисекунды проверен и после номера 9.

**Итоговая проверка T2:** 56 проверок HTTP-статусов плюс транзакционные и DB-проверки на временных данных; все исходные количества гостей, питомцев и событий сохранены после очистки. `prisma validate`, `npm run build:api`, `npm run check` успешны. Новые `*.spec.ts` не добавлялись, существующие не запускались.

### 6. P2 — Отсутствующее тело запроса вызывает HTTP 500

**Статус: исправлено 2026-09-08 (T1).** `PocketPetService.createPet` и `applyCareAction`, HTTP-контроллеры, [parser body](../../apps/api/src/pets/request-body.ts).

На момент аудита отдельные значения проверялись `parse*` функциями, но само `request` не проверялось. POST actions без тела привёл к `Cannot read properties of undefined (reading 'actionId')` и HTTP `500`.

**Что исправлено:** явный parser принимает только объект с известными полями; затем проверяются обязательные значения, имя и enum. Валидация происходит до чтений/записей сценария, даже если уже есть активный питомец. URL проверяется как UUID v4. Swagger отражает ограничения и ответы. Для защищённых запросов сначала требуется действующая cookie.

**Проверка критерия:** HTTP smoke подтвердил `400` для отсутствующего body, `null`, массивов, примитивов, пустых/длинных/нестроковых имён, неверных видов/длительностей/действий, лишних полей, некорректного JSON и UUID. Некорректные запросы не изменили гостя/питомца; корректное создание с trim имени, чтение, кормление, cooldown и `409` для второго питомца сохранили поведение. `npm run build:api` и `npm run check` (Prisma generate + API + Angular) выполнены успешно. SQL-патч применён к существующей локальной БД; `npm run db:push` подтвердил синхронизацию схемы без сброса. Новые `*.spec.ts` не добавлялись, существующие не запускались.

### 7. P2 — Динозавр механически отличается вопреки MVP-решению

**Статус: исправлено 2026-09-17 (T3).** `PocketPetService.createPet`, `pet-engine.resolvePetState`, [pocket-pet.config.ts](../../src/app/pocket-pet/pocket-pet.config.ts), RU/EN переводы, GDD §6.

На момент аудита species traits были нейтральными, но динозавр получал `medium` с множителем ухудшения 1.2. Кошка/собака/попугай получали `easy`, вопреки общему правилу одинаковых механик видов в MVP.

**Что исправлено:** все доступные виды создаются с `easy`; resolve также приводит старые `medium`/`insane` к `easy` перед расчётом. Сохранённые статы становятся отправной точкой; старая история и уже зафиксированный farewell не переписываются. UI динозавра показывает общий режим, RU/EN описание не обещает повышенной сложности. Dragon остаётся заблокирован.

**Проверка критерия:** все четыре доступных вида во всех трёх сохранённых режимах дали одинаковый результат на общей истории действий за сутки, с одинаковыми блокировками, энергией, mood и farewell. Создание через service проверено для всех видов в memory и PostgreSQL; старый `medium` динозавра записался как `easy` при GET. API service по-прежнему отклоняет dragon. Решение и применение к сохранениям закреплены в спецификации T3 и GDD.

### 8. P2 — Prisma repository обходит типизацию и маскирует повреждённые значения

**Статус: исправлено 2026-09-18 (T4).** [pet-record.mapper.ts](../../apps/api/src/pets/pet-record.mapper.ts), [prisma-pocket-pet.repository.ts](../../apps/api/src/pets/prisma-pocket-pet.repository.ts).

**Было:** преобразование прочитанных записей использовало `any` и fallback: неизвестный action превращался в `feed`, неизвестный вид — в `cat`, некорректная дата — в Unix epoch. Ошибка данных выглядела как нормальный питомец.

**Что исправлено:** mapper использует generated payload types и include через `satisfies`, явно проверяет enum, конечные числа/диапазоны, даты, JSON, обязательные связи и cooldown. Неожиданное значение вызывает `PetDataIntegrityError` с именем поля; HTTP не раскрывает внутренние детали. Известная нормализация режима из T3 сохранена.

**Проверка:** обе сборки прошли; ручной smoke проверил неверные enum/JSON/даты и отсутствующие связи. Повреждённый вид в PostgreSQL диагностирован без автоматической перезаписи. Типизированный mapper не содержит `any`.

### 9. P2 — Polling перезаписывает всю историю и создаёт много SQL-запросов

**Статус: частично улучшено.** `apps/api/src/main.ts`, `compose.yaml`, Prisma Studio 7.8 CLI.

| Сохранность | Временная smoke-сессия удалена точечно; прежние сессии и данные не сбрасывались |
| Watch API | Изменение mtime исходного файла вызвало пересборку, новый PID и успешный health |
| Ctrl+C | API, Angular и Studio остановлены; порты 3000/4200/5555 освобождены, PostgreSQL продолжает работать |
| Занятый порт / недоступная внешняя БД | Понятная ошибка и ненулевой exit code, чужие процессы не останавливаются |
| Защита сброса внешней базы | Команда отклонена; destructive reset не выполнялся |
| Воспроизведение дефектов | Polling/округление и коллизии ID — изолированный вызов engine; доступ без cookie и пустой body — отдельная временная сессия |

**Ограничения проверки:** Docker отсутствует, поэтому реальный Compose lifecycle не прогонялся. Автооткрытие системного браузера командой `dev:open` требует интерактивного Windows-сеанса; сами URL проверены в браузере. Полный многодневный UX и нагрузочная конкуренция не проверялись. Перезапуск/остановка проверены вне sandbox: sandbox Windows блокировал `taskkill` даже для созданных агентом процессов; это не требование запускать проект от администратора. При ранней диагностике Studio встречался `ERR_STREAM_UNABLE_TO_PIPE`: диагностический клиент не дочитывал HTTP body. Теперь `dev:doctor` полностью читает ответы; при заключительном запуске диагностики лог не повторился. Это наблюдение, а не отдельное исследование Prisma/Node. Angular 22 и Node 26 теперь являются совместимой конфигурацией.

## Предлагаемый порядок следующих задач

Порядок синхронизирован с [техническим треком GDD](../../GAME_DESIGN.md#144-техническая-готовность-и-очередность). GDD определяет этап и условие готовности; этот аудит хранит причины, воспроизведение и конкретные рекомендации.

1. `T1` — готово: гостевой guard и runtime validation (пункты 1 и 6).
2. `T2` — готово: единая защищённая операция изменения состояния, один активный питомец, уникальные события (2, 3, 5).
3. `T3` — готово: независимость времени от polling и нейтральные MVP-виды (4, 7); теперь можно оценивать баланс.
4. `T4` — готово: typed persistence, snapshot без истории, пагинация, один polling, последовательные команды и отдельные ошибки (8–11).
5. `T5` — готово: baseline migrations, общий контракт, закреплённый runtime и CI сборок (12–14); локальные проверки и первый Actions run прошли.
6. `T6` — готово: общие шкалы/даты, безопасные настройки и редактура RU/EN (15, 16); сборка, smoke и браузерная проверка пройдены. [Спецификация и результаты](../specs/ux-polish.md).

Пункт 17 и выполненная локальная часть пунктов 18–19 относятся к `T0`. Оставшиеся требования пункта 19 проверяются для конкретного хостинга перед публикацией; технические изменения T5 не являются deployment. При закрытии пункта нужно обновить его статус и доказательство здесь, затем статус соответствующего этапа в GDD.
