# Правила первого гостевого выпуска

**Статус, 2026-10-10:** ритм, длительность и сохранение скрытой энергии игрока согласованы владельцем. Тип задачи — продуктовый дизайн и первый инкремент реализации. Нулевая стоимость энергии и её скрытие входят в текущую правку; 21 день, возрастные границы и новый баланс ещё не реализованы. Последовательность — в [плане](../plans/guest-release-cycle.md).

**Принятые правила:** обычная сессия — 21 календарный день; ребёнок в дни 1–3, подросток 4–7, взрослый 8–21, затем прощание. Три возвращения суммарно на 4–8 минут: утром и вечером по 1–2 минуты, днём 2–4. Утром играть необязательно, достаточно базового ухода. Пропуски допускают мягкое восстановление. Дракон — будущий более требовательный режим, ориентир четыре визита / 10–15 минут. 1/3/7 дней нужны для тестирования.

**Уточнение по энергии:** сохранить `PlayerEnergy` в БД и контракте, восстановление и старые значения; все текущие действия стоят `0`. UI не показывает ни шкалу, ни стоимость. Энергия питомца остаётся. Отдельные правила ресурса для дракона пока не выбраны. Это уточняет предложение исследования об отказе от ограничителя, не удаляя саму модель.

**Добавлено в roadmap:** укладывание только при достаточной усталости, пробуждение только после достаточного отдыха. 5–12 часов — ориентир щадящего сна без штрафа хозяину; порог укладывания, минимум отдыха и поведение после 12 часов ещё нужно спроектировать. Питомец должен уставать к вечеру при обычном ритме без обязательной утренней игры. Сейчас сохраняется свободный переключатель света; новый сон не реализуется в инкременте энергии.

**Осталось выбрать:** возраст аудитории, смысл итоговой оценки и точные правила сна. [Исследование](../reports/pet-care-rhythm-2026-10-10.md) и расчёты ниже сохраняются как исходные наблюдения до изменения стоимости энергии; они не подтверждают баланс будущих 21 суток.

## Текущее состояние и расчёт ритма

Источник — `pet-engine.ts`, `pet-question-rules.ts` и [backend spec](backend-source-of-truth.md#t3-время-и-нейтральность-видов-решение-2026-09-17). Расчёт выполнен 2026-10-10 на backend версии `24a2139`; существующее локальное исправление маршрута комнаты на него не влияет.

Для сравнения использованы настоящие функции engine с явным временем, без HTTP и БД. Создание — в 08:00; два визита — 08:00/22:00, три — 08:00/15:00/22:00. При визите: включить свет, если выключен, → кормление → уборка → выбранная активность. В 22:00 свет выключается. Утреннее действие ровно в момент завершения уже не выполняется. Все действия внутри визита имеют одно время; лишнего ожидания cooldown нет.

| Ритм и активность                                   | 1 день: итог / балл | 3 дня: итог / балл | 7 дней: итог / балл | Сытость / здоровье на 7-й день |
| --------------------------------------------------- | ------------------- | ------------------ | ------------------- | ------------------------------ |
| 2 визита, игра только утром                         | `grown` / 75.9      | `grown` / 52.7     | `grown` / 50.8      | 0 / 0                          |
| 2 визита, игра при каждом визите                    | `grown` / 74.4      | `grown` / 53.2     | `grown` / 53.2      | 0 / 0                          |
| 3 визита, игра только утром                         | `grown` / 81.3      | `grown` / 79.8     | `grown` / 77.0      | 70 / 59.8                      |
| 3 визита, игра при каждом визите                    | `grown` / 75.6      | `grown` / 64.0     | `grown` / 53.2      | 0 / 0                          |
| 3 визита, утренняя/вечерняя игра и дневная прогулка | `grown` / 75.3      | `grown` / 63.6     | `grown` / 53.2      | 0 / 0                          |

В этих сценариях не было отказов по cooldown или энергии. Минимум энергии игрока после действия — 80 без прогулки и 75 с прогулкой. Это не полная проверка ресурсных ограничений.

**Наблюдение:** при трёх кормлениях и трёх играх поступает до 90 сытости в сутки, а расходуется 72 от времени и 36 от игр. Дефицит — минимум 18; ограничение сытости сверху может увеличить фактическую потерю. Даже без штрафов здоровье теряет 9.6 в сутки, а три кормления возвращают 6. Прогулка помогает здоровью, но дополнительно расходует сытость и энергию питомца.

**Наблюдение:** `grown` при нулевых сытости и здоровье соответствует действующей формуле. Остальные показатели 72/94/100 дают среднее 53.2. Поэтому один положительный итог не подтверждает подходящий баланс. В сценарии трёх игр пропуск всех визитов второго дня даёт 50.8 за три дня и те же 53.2 за семь дней; финальное среднее скрывает различие историй.

### Пробная настройка, не принятое изменение

Чтобы оценить объём следующей реализации, отдельно сравнили кормление `+40` сытости / `+4` здоровья вместо `+30` / `+2`. Менялись только параметры загруженного модуля в памяти процесса; исходники, БД и сохранения не затрагивались. Остальные правила остались прежними.

Эти числа нельзя считать готовым балансом. После выбора ритма отдельно оценить восстановление здоровья, а не только рост итогового среднего.

## Варианты финала

| Вариант                                               | Смысл для игрока                                                               | Объём изменения и ограничения                                                                                                                                                                                                                 |
| ----------------------------------------------------- | ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Текущее среднее финальных статов                      | «В каком состоянии питомец подошёл к прощанию»                                 | Хранение уже реализовано. Поздний уход может перекрыть прошлые пропуски; высокие три шкалы компенсируют две нулевые. Требуется честное объяснение этого смысла                                                                                |
| Финальные показатели с условием по критическим шкалам | «К прощанию достаточно общего благополучия и нет критически плохого состояния» | Отдельное продуктовое изменение порогов `grown`/`left`; прежде нужно выбрать критические шкалы и условия. Прошлая забота по-прежнему напрямую не учитывается                                                                                  |
| Оценка за всю жизнь                                   | «Как питомцу жилось на протяжении сессии»                                      | Нужна спецификация формулы и перехода для существующих питомцев. Среднее по запросам или событиям зависит от частоты открытия игры; предпочтительно считать по времени. Понадобится согласовать накопление, хранение и отображение результата |

**Ограничение:** среднее пяти шкал за всю жизнь тоже может скрывать длительно низкие сытость и здоровье. Сам выбор временного усреднения эту проблему не устраняет. Оценка всей жизни не равна числу нажатий и не должна требовать постоянного онлайна.

**Предложение для любого изменения:** уже сохранённые финалы и история остаются неизменными. Для активных питомцев заранее описать, с какого момента действуют новые правила; не восстанавливать неизвестную прошлую оценку выдуманными значениями.

## Остаток Q3 и проверка выбранных правил

- Для трёх разговоров в сутки за семь дней банк уже проверен без повторов; при четырёх есть два повтора подростковой категории. Это модель из [плана Q3](../plans/q3-question-content.md), а не оценка детской сложности или обязательное число разговоров.
- Дополнительный расчёт 21 исхода за неделю: все верные ответы дают доверие 92, все неверные — 29, все отказы сохраняют 50. В выбранной модели игры доводят радость до потолка, поэтому её финальное значение одинаково; это не означает отсутствия промежуточного эффекта вопросов. Здесь проверены чистые эффекты, не выдача/сохранение попыток.
- После выбора аудитории проверить формулировки и объяснения RU/EN с предполагаемым игроком. Возраст питомца задаёт категорию вопроса, но не заменяет возрастную оценку читателя.
- Для выбранного баланса сравнить 1/3/7 дней, обычный ритм, пропуск дня и восстановление, сочетания игр/прогулок/вопросов, оба финала. Фиксировать отдельные шкалы и причины отказов, а не только `grown`/`left`.
- При реализации выполнить узкий расчёт engine, сборку API и затронутые пользовательские сценарии. Если меняются хранение/контракт/UI — обе сборки и соответствующие проверки границ. Автотесты и система подготовки состояний остаются отложенными по GDD §14.5.
