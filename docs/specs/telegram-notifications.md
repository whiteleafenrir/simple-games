# Уведомления Telegram и подключение из профиля

## Статус и объём

**Решение владельца, 2026-10-10:** подготовить раздел профиля для подключения Telegram. Сервер бота реализуется отдельным приложением позднее. Основа — [roadmap GDD §14.2.3](../../GAME_DESIGN.md#1423-система-уведомлений).

**Текущий инкремент реализован, 2026-10-10:** интерфейс и игровая часть API для выдачи/отзыва кода. Обработчик бота, погашение кода и доставка остаются следующим этапом. Пока бот не запущен, UI показывает это явно и не сообщает об успешном подключении.

**План:** добавить таблицу кодов и гостевые методы API → карточку профиля с RU/EN → проверить миграцию на отдельной БД, API и браузер → отметить результат. Игровые правила и пользовательские питомцы не меняются.

## Хранение и границы приложений

**Предлагаемая архитектура:** одна PostgreSQL-база остаётся источником истины, Prisma schema и миграциями управляет игровой API. Привязка Telegram относится к игроку (сейчас — к гостевой сессии), а не к отдельному питомцу, поэтому переживает завершение истории и создание следующего питомца.

Бот — отдельный процесс в монорепозитории, со своим секретом Telegram и жизненным циклом запуска. Он общается с игровым API через защищённые внутренние методы. Прямой доступ бота к игровым таблицам и вторая копия состояния не требуются. Это позволяет менять схему хранения без одновременного обновления бота; сбой Telegram не должен блокировать уход за питомцем.

В будущем игровой backend планирует события и сохраняет очередь отправок. Бот получает задания, отправляет сообщения и сообщает результат. Повторы, лимиты, отмена заданий при отключении, авторизация между сервисами и транспорт очереди описываются до реализации доставки. Уведомления должны работать при закрытой игре, независимо от браузерного polling.

## Сценарий подключения

1. В профиле есть отдельный раздел «Уведомления» с карточкой Telegram. Альбом питомцев остаётся доступным.
2. Игрок запрашивает одноразовый код. Backend проверяет гостевую cookie; привязка никогда не использует публичный guest id или секрет этой cookie как код.
3. Код можно скопировать в личный чат с ботом. После настройки адреса бота кнопка открывает ссылку с параметром `start`, затем игрок запускает бота.
4. Будущий бот передаёт код и Telegram user/chat id в защищённый внутренний API. Backend атомарно проверяет и погашает код, создаёт привязку.
5. Профиль показывает подтверждённое сервером подключение; отключение отзывает привязку и незавершённый код.

Код — случайный токен ограниченного срока действия; в БД хранится только хеш. Frontend не создаёт код самостоятельно и не сохраняет его в localStorage. Копирование или переход в Telegram сами по себе не означают успешную привязку. До появления бота интерфейс явно сообщает, что подключение пока недоступно.

Привязка разрешает только доставку уведомлений. Она не становится способом входа в игру или восстановления гостевой сессии.

## Первый инкремент: код подключения

- `TelegramLinkCode`: одна строка на гостя, уникальный SHA-256 хеш, `expiresAt`; связь с `GuestSession` с каскадным удалением. Отдельная добавочная SQL-миграция; данные питомцев и гостевые cookie сохраняются. Применение через `npm run db:deploy`.
- Код: 32 случайных байта в base64url, срок **10 минут** — стартовое техническое допущение. Повторная выдача заменяет прежний код атомарным upsert. Исходный токен возвращается только при создании, после перезагрузки нужно выпустить новый. Код только в памяти открытого компонента.
- Защищённые гостевой cookie методы `/guest-sessions/:guestId/telegram`: `GET` возвращает срок действующего кода либо `null` и текущую недоступность бота; `POST /link-code` с `{}` создаёт код; `DELETE /link-code` отзывает его. Ответы `Cache-Control: no-store`. Чужой guest id запрещён тем же guard, что защищает питомцев.
- До запуска бота пользователь может создать, скопировать или отозвать код, но не завершить подключение. UI объясняет это до выдачи. Ссылки на несуществующего бота нет. Отсчёт срока — подсказка UI; окончательную проверку при погашении выполнит backend будущего этапа.
- Таблица успешных привязок и внутренний метод погашения добавляются вместе с сервером бота; сейчас API не возвращает фиктивное состояние «подключено».

## Дальнейшие решения

- События, частота, тихие часы и взаимодействие нескольких каналов.
- Адрес бота, запуск его сервера и защищённый контракт обмена с игровым API.
- Повторная привязка и перенос гостя в аккаунт; для первого инкремента срок и перевыпуск описаны выше.

## Проверка

RU/EN, светлая/тёмная темы, desktop и узкий экран, доступность с клавиатуры. Пользователь видит реальную доступность подключения. Новые постоянные автотесты не добавляются.

**Выполнено, 2026-10-10:** `npm run check` (Prisma Client, API, Angular), `npm run lint`. На изолированной схеме PostgreSQL прошли проверки 401/403, строгого body, `no-store`, случайного кода/хеша, истечения срока, 12 одновременных перевыпусков, изоляции гостей и повторного отзыва. Миграция проверена на отдельной схеме и применена локально; число строк в прежних таблицах не изменилось, `npm run db:check` не обнаружил drift. У локального пользователя нет права создавать отдельную БД, поэтому использованы временные схемы; из-за сравнения разных namespace в `migrate dev` SQL сформирован через `migrate diff` по изолированной схеме, без reset.

**Ограничение проверки интерфейса:** в браузере проверены отображение карточки и состояние ошибки. Запущенный на порту 3000 старый API ещё не содержит новых маршрутов; после перезапуска `npm run dev` нужно пройти выдачу/копирование/отзыв через UI, RU/EN, обе темы и узкий экран. Успешная привязка и отправка в Telegram не проверялись: сервер бота отложен владельцем.
