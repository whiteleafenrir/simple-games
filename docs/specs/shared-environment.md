# T5: миграции, общий контракт и CI

**Решение 2026-09-18. Тип:** implementation/refactor для A12–A14 аудита. Игровые правила, HTTP-формат и баланс не меняются.

## Миграции

- Начальная миграция фиксирует схему после T4: семь таблиц, связи, уникальный token hash, частичный индекс одного активного питомца и индекс истории. SQL и неизменяемый снимок Prisma schema baseline хранятся в Git.
- Новая БД и обычный `dev:setup` используют `prisma migrate deploy`, затем явную генерацию Client. `db push` остаётся только инструментом прототипирования на отдельной одноразовой БД.
- Для существующей базы после T4 предусмотрен `db:baseline`: сначала read-only сравнение с замороженной baseline schema и проверка счётчиков истории, затем `migrate resolve --applied`. При drift команда останавливается до регистрации baseline. Питомцы, события и cookie не переписываются. Повтор уже зарегистрированного baseline допустим.
- Старые SQL-патчи остаются историческим путём до T4. Для более старой БД сначала применяются все патчи в порядке T1 → T2 → T4, затем проверка baseline. Никаких автоматических reset или согласия на потерю данных.
- Новые изменения оформляются отдельными SQL migrations через `prisma migrate dev` на dev-базе. Общее окружение запускает только `db:deploy`; backup/restore выполняется до изменения важных данных.

## Контракт

- Локальный npm workspace `@simple-games/pet-contract` содержит только TypeScript transport types: идентификаторы, guest, snapshot, история, результат действия и тела запросов.
- Angular и Nest используют один пакет через type imports/re-exports. Он не содержит engine, зависимостей от Nest/Prisma/Angular, runtime-кода или секретов; путь запуска собранного API сохраняется.
- HTTP-body на сервере остаётся `unknown` до runtime validation. Общие request types описывают форму; доступность вида, границы имени и остальные правила всё равно проверяет сервер.
- Баланс, длительности сессий и стоимость действий остаются в API. UI-метаданные показывают те же 1/3/7 дней; при изменении баланса их нужно сверять отдельно. Полные OpenAPI response schemas и генерация клиента не нужны для выбранного пути с общими типами.

## CI и приёмка

- GitHub Actions на push и pull request: Node из `.nvmrc`, закреплённый npm, `npm ci`, Prisma validate/generate, API build и Angular build. PostgreSQL service проверяет применение миграций на пустую БД, повтор deploy и отсутствие schema drift.
- Локальная проверка: обе сборки; пустая временная БД; существующая схема T4 с fixture-данными → baseline → повторный deploy; отказ baseline при drift; сохранность данных и DB-инварианта. Backup/restore проверяется на временной БД.
- Новые `*.spec.ts` и запуск тестового покрытия не входят в этап. Реальный запуск Actions подтверждается отдельно после push.

## Результаты проверки 2026-09-18

- `npm run check` прошёл. В отдельной копии проекта без `.env` и `node_modules` выполнены `npm ci --offline`, `dev:setup` на пустой PostgreSQL 17.10 и обе сборки; начальная миграция применяется автоматически. Angular bundle остался 410.30 kB.
- Ручной smoke на отдельном PostgreSQL прошёл 15 групп проверок: новая и заполненная БД, повтор baseline/deploy, нулевой drift, отказ при лишней колонке и неверном счётчике, уникальность активного питомца, backup/restore и запуск собранного API. После baseline cookie восстанавливает прежнего гостя; snapshot, история и action result сохраняют формат, неверное действие даёт `400`, запрос без cookie — `401`.
- `pg_dump`/`pg_restore` восстановили fixture-данные всех семи таблиц и migration history. Временные базы smoke удалены. Это проверка инструментов на локальной PostgreSQL; backup/restore выбранного хостинга нужно подтвердить отдельно.
- До регистрации baseline локальной БД сохранена резервная копия в игнорируемом `.local/`. После baseline и `dev:setup` хеши всех семи игровых таблиц совпали. `db:check` не обнаружил drift, `db:migrations:status` подтвердил актуальность схемы.
- На момент локальной проверки CI workflow был добавлен, но ещё не отправлен в remote. Новые `*.spec.ts` не добавлялись, тестовое покрытие не запускалось.
