# T4: устойчивость данных и клиента

**Решение 2026-09-17. Тип:** bug fix/refactor для A8–A11 аудита. Баланс и правила действий из T3 сохраняются.

**Текущее состояние:** реализовано и проверено 2026-09-18.

## Данные и API

- Prisma repository читает generated payload types. Строковые enum, даты, числовые поля, JSON-снимки, обязательные связи и cooldown проверяются явно. Повреждение вызывает диагностическую ошибку с именем поля, без подстановки другого вида/действия и без перезаписи записи. HTTP возвращает обычную серверную ошибку, подробности остаются в серверном логе.
- `OwnedPet` становится текущим snapshot: вместо `careHistory` содержит `careHistoryCount`. Действие возвращает snapshot и `historyEntry` (одно новое событие либо `null` при игровом отказе). Движок не нуждается в прежних событиях; ID сохраняет номер события внутри питомца.
- История: `GET /guest-sessions/:guestId/pets/:petId/history?cursor=...`. Ответ `{ items, nextCursor }`, по 50 событий от новых к старым, порядок `(appliedAt DESC, id DESC)`. Курсор содержит время и ID последнего показанного события; новые действия не сдвигают следующие страницы. Некорректный курсор — `400`, чужой питомец — `404`; действуют общие guest guard и no-store.
- Чтение snapshot не загружает и не проверяет всю историю. Запись добавляет только переданное новое событие; повтор идентичного события допустим, конфликт содержимого/владельца откатывает транзакцию. Cooldown/статы/энергия/farewell сохраняются только при изменении. Завершённые питомцы при GET вычисляются для ответа без повторной записи неизменного итога; восстановление энергии игрока в ответе сохраняет правило T3.
- `Pet.careHistoryCount` хранится атомарно с новым событием. Существующая история получает точный count через повторяемый SQL-патч `prisma/patches/2026-09-17-pet-history-snapshots.sql`; добавляется индекс `(petId, appliedAt, id)`. Патч применяется до `npm run db:push`, под блокировкой таблиц и без удаления данных. Пустая база создаётся через schema; baseline migrations остаются T5.
- Контракт snapshot меняется одновременно на API и Angular. Перед обновлением нужно остановить старый API: прежний код не поддерживает счётчик истории. Старые ID и JSON истории сохраняются.

## Клиент

- Store выполняет один опрос раз в 30 секунд, пропускает его в скрытой вкладке и обновляет при возвращении. Компоненты не запускают второй таймер/начальную загрузку.
- Snapshot-загрузки объединяются, загрузки и команды выполняются последовательно. Старый GET не может перезаписать результат более новой команды. Повторный клик блокируется синхронным pending-флагом до окончания команды. Запросы ограничены таймаутом 20 секунд.
- Ошибки синхронизации и команды независимы, представлены ключами RU/EN переводов. Ошибка первого GET остаётся видимой; фоновый GET очищает только ошибку загрузки. Успешная повторная команда очищает только свою ошибку. Сеть/таймаут, `400`, `401/403`, `404`, `409` и серверная ошибка имеют понятные тексты. Для загрузки доступна кнопка повтора; последний успешный snapshot остаётся видимым.
- История загружается только в профиле конкретного питомца, имеет состояния загрузки/ошибки и кнопку «Показать ещё». Смена питомца или его счётчика сбрасывает страницы; устаревший ответ истории игнорируется. Ошибка следующей страницы сохраняет уже показанные записи и позволяет повторить запрос.

## Проверка и результат

- `npm run build:api`, `npm run check` и сборка Angular после последней правки интерфейса прошли. Новые `*.spec.ts` не добавлялись.
- SQL-патч дважды применён к локальной базе: повтор безопасен, счётчики совпадают с историей, хеши прежних значений всех семи таблиц сохранились. `db push` подтвердил соответствие схемы.
- Ручной smoke Nest/PostgreSQL на временных гостях прошёл 35 проверок HTTP, проверки rollback, повторов/конфликтов событий, диагностики повреждённых записей и in-memory parity. Два экземпляра API сохранили ограничения при параллельных созданиях и действиях. Временные гости удалены; хеши исходных данных не изменились.
- При 0 и 1000 событий опрос активного питомца выполняет 11 SQL-запросов и не читает `PetCareAction`. Проверена пагинация всех 1000 событий, включая одинаковое время и вставку нового события между страницами, без сдвигов и повторов. Неизменный архив при GET не перезаписывается. Это проверка числа запросов, а не нагрузочный benchmark.
- Ручная проверка store с управляемыми ответами подтвердила первый failed GET и повтор, последовательность медленных GET/команд, блокировку двойного клика, отдельные ошибки загрузки/команды, восемь вариантов ошибок, паузу в скрытой вкладке, обновление при возвращении и игнорирование ответа после уничтожения store.
- В браузере с отдельным локальным fixture API проверены ошибка первой загрузки и повтор, pending действий, сохранение ошибки `400` после успешного GET и её очистка после повторной команды. История показала 50 → 100 → 121 запись; ошибка следующей страницы сохранила первые 50 и позволила повтор. Вёрстка проверена по снимкам экрана. Смена маршрута во время запроса истории отдельно в браузере не проверялась; защита реализована номером запроса и cleanup эффекта.
- Регрессия времени T3: 1452 численных сравнения за час/сутки/неделю с разной частотой resolve, сном, действиями, порогами и farewell; максимальная разница `4.78e-10`.
